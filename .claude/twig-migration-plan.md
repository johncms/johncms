Рабочий документ (gitignored). Статус: **этапы 0–2 закрыты, идёт этап 3** (публичные модули,
20 модулей из ~18 переведены — публичная часть закрыта). Открытых вопросов нет. Отмечай прогресс галочками `[x]` в
разделе 8.

Дата анализа: 31.07.2026, последняя правка 06.08.2026. Ветка `10.x`, CMS_VERSION 9.9, PHP 8.2.

**С чего продолжать в новой сессии:** прочитать `.agents/twig-migration.md` (рецепт миграции
модуля), затем этап 4 — админка и слияние тем. Публичных `.phtml` не осталось; удалить

## 1. Краткое резюме

Текущий шаблонизатор — `mobicms/render` 2.0 (клон Plates). 290 файлов `.phtml`
(258 в модулях, 32 в темах и инсталляторе), 218 PHP-файлов так или иначе трогают `Render`.

Ключевые выводы:

1. **Все 14 требований выполнимы, но три из них сформулированы не так, как их выгоднее
   реализовать.** Разбор в разделе 5: фоллбэк надо делать N-уровневым (через `parent` в
   манифесте темы), переключатель «Twig / старый движок» — по имени шаблона, а не по модулю,
   а разделение админки и публички — это namespace'ы, а не отдельные окружения
   (решение от 04.08.2026, 5.2).
2. **Требования не покрывают три обязательных вещи**, без которых миграция ломает систему:
   извлечение переводов из `.twig` (2015 вызовов `__()` в шаблонах, сканер понимает только
   `.php`/`.phtml`), рендеринг писем и инсталлятора вне HTTP-контекста, и инвентаризация
   «намеренно неэкранированного» вывода перед включением autoescape.
3. **Переход — хороший момент закрыть четыре застарелых архитектурных дефекта** (раздел 4):
   сниффинг `$_SERVER['REQUEST_URI']` в двух местах, мутабельное состояние движка-синглтона,
   service locator (`di()`, `$container->get()`) и SQL-запросы внутри layout'ов, и ручное
   экранирование (737 вызовов `$this->e()`, каждый пропуск — XSS).
4. **Побочный выигрыш по безопасности, который стоит отметить отдельно**: сегодня тема — это
   произвольный PHP-код, то есть установка чужой темы = RCE. Тема на Twig — это данные;
   шаблон может вызвать только то, что мы явно зарегистрировали.

**Целевая схема.** Граница проводится по правилу *разные возможности → разные окружения,
разная вёрстка → разные namespace'ы*:

* окружений три — `web` (весь HTTP), `mail`, `install`; последние два отличаются не вёрсткой,
  а тем, что там нет запроса, csrf и Vite;
* тема одна на весь сайт, админская вёрстка — namespace `@admin` внутри неё; шаблон явно
  называет источник (`{% extends '@admin/layouts/default.twig' %}`), поэтому вопрос «мы в
  админке?» в рантайме почти исчезает;
* один `FilesystemLoader`, на каждый namespace — упорядоченная цепочка путей
  (тема → родительская тема → дефолтная тема → модуль), зарегистрированная один раз при
  сборке окружения по соглашению об именах, поэтому новый модуль не требует правки
  конфигурации;
* контроллеры работают с `RendererInterface` и постепенно переходят на возврат `ViewResponse`.

Объём работ: ~290 шаблонов + слияние двух форкнутых тем, 6 этапов, каждый оставляет систему
рабочей.

## 2. Что есть сейчас (факты)

### 2.1. Движок

`Johncms\System\View\Render extends Mobicms\Render\Engine`, расширение `phtml`, синглтон
контейнера через `RenderEngineFactory`.

```
Engine::addFolder(string $name, string $directory, array $search = [])
TemplateName::getPath() → array_reverse($folder) → первый существующий файл
```

То есть порядок поиска: **последний добавленный путь → первый**. `Render::addFolder`
подкладывает в `$search` путь текущей темы, поэтому реальная цепочка сегодня:

```
themes/<skindef>/templates/<namespace>/<file>.phtml   ← если тема не 'default'
modules/<namespace>/templates/<file>.phtml
```

Для namespace `system` — `themes/<skindef>/templates/system` → `themes/default/templates/system`.

**Переопределение шаблонов модулей темой работает уже сейчас** и оформлено как образец в
`themes/example/`: вся тема — это один файл

```
themes/example/templates/homepage/index.phtml
```

При `skindef = example` он подменяет главную страницу модуля `homepage`, а всё остальное
фоллбэчится само: layout берётся из `themes/default/templates/system/layout/default.phtml`
(каталога `system` в теме `example` нет), ресурсы — из `public/themes/default/assets`.
Источник шаблона нигде не указывается, поиск автоматический. То есть требование №1 в этой
части описывает **уже существующее поведение, которое надо сохранить**.

**Чего действительно нет — среднего уровня цепочки.** Для шаблонов модулей уровней сегодня
два (`тема → модуль`): `themes/default/templates/` содержит только `system`, папок модулей
там нет, и `Render::addFolder` подкладывает в поиск ровно один путь — текущей темы.
Практических следствий два:

* дефолтная тема не может переопределить шаблон модуля для всех тем сразу;
* тема не может наследоваться от другой темы, поэтому «то же, что `default`, но с другим
  сайдбаром» приходится копировать целиком.

Именно эта часть требования №1 расширяет поведение, а не сохраняет его — и ради неё в
разделе 5.1 предлагается сразу N-уровневая цепочка через `parent` в манифесте темы.

### 2.2. Окружения

Разделения окружений как концепции нет. Есть подмена:

```php
// RenderEngineFactory
if ($this->isAdmin()) {                      // parse_url($_SERVER['REQUEST_URI'])
    $engine->setTheme('admin');
    $engine->addFolder('system', THEMES_PATH . 'admin/templates/system');
} else {
    $engine->setTheme($config['skindef']);
    $engine->addFolder('system', THEMES_PATH . 'default/templates/system');
}
```

Имя `system::layout/default` резолвится в разный файл в зависимости от URL. Именно поэтому
`modules/news/templates/admin/index.phtml` и `.../public/index.phtml` пишут одну и ту же строку
`$this->layout('system::layout/default')` и получают разные layout'ы. Та же логика
продублирована в `Assets::isAdmin()`.

### 2.3. Регистрация namespace'ов

Ленивая, из конструктора контроллера: `ControllerContext::initModule('news')` →
`addFolder('news', MODULES_PATH . 'news/templates/')`. Плюс ручные регистрации
(`libraryHelpers` в 4 контроллерах модуля library).

Следствие: шаблон модуля A может подключить шаблон модуля B только если B тоже был
проинициализирован в этом запросе. Такие пересечения уже есть в коде:
`themes/default/templates/system/pages/result.phtml` подключает `admin::sidebar-admin-menu`
(шаблон админ-модуля из фронтовой темы).

`Render::addFolder` пришлось делать идемпотентным — синглтон переживает запрос, а контроллеры
регистрируют namespace в конструкторе; второй запрос в одном процессе падал с
`The template namespace "forum" is already being used.`

### 2.4. Layout'ы и секции

Страница сама выбирает layout: `$this->layout('system::layout/default')` — 241 вызов.
Layout'ов всего три: `default` (frontend), `default` и `guest` (admin), плюс
`system::mail/layouts/default`.

Секции: `section()` 20, `push()` 7, `sectionReplace()` 3, `start/stop` 7.
`fetch()` (подключение партиала) — 148.

### 2.5. Данные шаблонов

Глобальные — через `Engine::addData()` в `RenderEngineFactory`: `container`, `config`, `locale`,
`user`, `csrf_token`. Плюс `AdminControllerContext::initModule()` добавляет `regtotal`,
`countusers`, `countadm`, `bantotal` — **четыре SQL-запроса на каждый запрос к админке**,
даже если сайдбар не рендерится, и они кэшируются в синглтоне между запросами.

Внутри layout'а фронтенда:

```php
$counters = $container->get('counters');
$ads = di(Johncms\Ads::class);
$theme = di(\Johncms\System\View\Theme::class);
$currentPage = di(\Johncms\Http\CurrentPage::class);
```

### 2.7. Ресурсы

* Исходники сборки: `themes/<name>/src/{scss,js}` → Vite → `public/build/` (манифест).
* Статика: `public/themes/<name>/assets/` — **отдельное дерево, в `themes/<name>/` его нет**.
* `Assets::url()` для фронтенда ищет `skindef → default`, для админки — только `admin`,
  и **бросает исключение**, если файла нет. Отсюда `try { ... } catch (Exception) {}` вокруг
  подключения локали flatpickr в layout'е.
* Точки входа Vite захардкожены в `vite.config.js` (два массива путей) — новая тема требует
  правки конфига сборки.

### 2.8. Рендеринг вне HTTP

* **Письма**: `Mail\EmailSender::send()` берёт `di(Render::class)` из планировщика (CLI),
  мутирует общий движок (`addData(['locale' => ...])`) и рендерит
  `system::mail/templates/*`. В CLI `$_SERVER['REQUEST_URI']` нет → всегда фронтовая тема.
* **Инсталлятор**: `public/install/index.php` создаёт **свой** `new Render('phtml')` с
  namespace'ами `system` (дефолтная тема) и `install`.
* **Страницы ошибок**: `ExceptionResponseFactory` рендерит `system::error/404` через общий движок.
* **Пагинация**: `Http\Pagination\Pagination::render()` — сервис, который рендерит
  `system::app/pagination` и возвращает HTML-строку.

### 2.9. Локализация

`composer translate-scan` → `I18nScanCommand` → `translate.xml.dist` (домен → список
`sourceDir`) → `gettext/php-scanner`. Фильтр файлов:

```php
preg_match('/^.+\.(?:phtml|php)$/i', $path)
```

`.twig` сканер не увидит.

## 4. Проблемы текущей реализации, которые надо закрыть вместе с миграцией

### 4.1. Сниффинг `$_SERVER['REQUEST_URI']` (блокер)

`RenderEngineFactory::isAdmin()` и `Assets::isAdmin()` читают суперглобал. Это прямо
противоречит недавно завершённой работе «запрос — не сервис» и правилу из
`.agents/architecture.md` («шаблон получает факты, а не запрос»), ломается в CLI и в
worker-рантайме отдаёт первый запрос процесса.

**Решение: вопрос «мы в админке?» исчезает целиком, а не переезжает.** Шаблон страницы сам
называет namespace (`{% extends '@admin/layouts/default.twig' %}`), а модульные шаблоны знают
свой контекст статически — они лежат в `templates/admin/` или `templates/public/`.

Шаблоны, живущие сегодня «в обоих мирах» (`error/403`, `error/404`, `pages/result`),
**разделяются на два файла даже там, где вёрстка совпадает** — чистота важнее экономии на
паре файлов, а сами шаблоны выбирает вызывающий код. Никакого атрибута запроса и никакого
резолвера для этого не нужно, потому что **механизм уже есть в кодовой базе**:

| Шаблон | Кто называет | Как сейчас |
| --- | --- | --- |
| `error/404` | тот, кто бросает | `pageNotFound(string $template = 'system::error/404', …)` — шаблон первым аргументом, `PageNotFoundException::setTemplate()`. Все 404 сейчас идут с дефолтом, ни одного явного вызова нет |
| `error/403` | middleware доступа | `AdminAccessMiddleware` и `SuperAdminAccessMiddleware` уже указывают `'system::error/403'` литералом и по определению знают, что они админские |
| `pages/result` | контроллер | 196 вызовов, все с явным именем шаблона; каждый контроллер знает свой контекст статически |

То есть на миграции админский код просто пишет `@admin/pages/errors/404.twig` там, где
публичный пишет `@theme/pages/errors/404.twig` — строка в том же вызове, который и так
переписывается при переводе шаблона на Twig. Дополнительной работы это не создаёт.

**Единственный остаток:** 404 по URL, не совпавшему ни с одним маршрутом (`/admin/чепуха`),
бросается ядром с шаблоном по умолчанию и отрендерится публичным. Это допустимо и, пожалуй,
корректно: несуществующий URL не находится «внутри админки» ни в каком осмысленном смысле.

Что остаётся из этого пункта — убрать `$_SERVER['REQUEST_URI']` из `RenderEngineFactory` и
`Assets`; после слияния тем (3.1) им обоим просто нечего больше выбирать.

### 4.2. Мутабельное состояние движка-синглтона

`addFolder`/`addData` мутируют общий объект в течение запроса и переживают его. Из-за этого
уже пришлось делать `addFolder` идемпотентным (иначе второй запрос в процессе падал).

**Отдельно про `locale` в `EmailSender` — это не баг, а требование.** Письмо отправляется на
языке получателя, поэтому цикл перед каждым сообщением выставляет и переводчик, и переменную
шаблона:

```php
$translator->setLocale($item->locale);
TranslatorFunctions::register($translator);   // Gettext, статика на весь процесс
$view->addData(['locale' => $item->locale]);
```

Каждое письмо получает свой язык — так и должно быть. Проблема в том, что **ничего не
восстанавливается после цикла**: глобальный биндинг `__()`/`d__()` (изначально
установленный в `bootstrap.php:90`) и `locale` в синглтоне `Render` остаются от последнего
письма. Сегодня это безвредно — очередь отправляется только из планировщика, процесс сразу
завершается. Опасность отложенная: вторая задача планировщика в том же процессе получит
чужой язык, а в worker-рантайме — веб-запрос.

**Требование, которое отсюда следует:** локаль должна быть **параметром рендеринга**, а не
окружающим состоянием.

```php
$this->mailRenderer->render($item->template, $item->fields, locale: $item->locale);
```

Внутри — скоуп с гарантированным восстановлением, пока глобальные gettext-функции живы:

```php
$this->translator->withLocale($locale, fn () => $twig->render($template, $data + ['locale' => $locale]));
```

Целевое состояние: i18n-runtime Twig держит `TranslatorInterface`, у которого локаль
скоупится на вызов; глобальные `__()`/`d__()` остаются для PHP-кода и делегируют в тот же
сервис. Тогда «язык на письмо» перестаёт быть мутацией общего объекта и становится обычным
аргументом.

**Остальное состояние** в Twig-архитектуре не мутируется вовсе: namespace'ы известны из
конфигурации модулей, per-request данные приходят через глобал `app` поверх `RequestStack`.

**Решение.** В Twig-архитектуре окружение собирается один раз и **не мутируется**:
namespace'ы известны из конфигурации модулей, per-request данные приходят только через
глобал `app`, который тонкой обёрткой ходит в `RequestStack` (тот же приём, что уже
используют `CurrentPage`, `Theme`, `Environment`). Ничего сбрасывать между запросами не нужно.

### 4.3. Service locator и SQL в layout'ах

`di()`/`$container->get()` внутри `.phtml` (13 вызовов, из них 4 — в основном layout'е) и
4 SQL-запроса в `AdminControllerContext` на каждый запрос к админке.

**Решение.** `Twig\RuntimeLoader\ContainerRuntimeLoader`: расширение объявляет функции,
зависимости живут в runtime-классе, который контейнер создаёт **только если шаблон реально
вызвал функцию**. Счётчики админки становятся ленивым runtime — запросы уходят из
горячего пути на страницы без сайдбара.

### 4.4. Ручное экранирование

737 `$this->e()`. Любой пропуск — XSS, и ревьюеру приходится проверять это глазами
(`.agents/review/security.md`). Autoescape закрывает класс уязвимостей целиком.

Обратный риск при миграции описан в 5.7 — механическая замена `<?= $x ?>` → `{{ x|raw }}`
недопустима.

### 4.5. Мелочи, которые всплывут

* `Johncms\System\View\Theme` — это **цветовая схема** (dark/light/auto из cookie), а не тема
  оформления. Имя занято и будет путаться. Переименовать в `ColorScheme`.
* `themes/default/templates/system/pages/result.phtml` тянет `admin::sidebar-admin-menu` —
  фронтовый шаблон лезет в админский, и делает это через `sectionReplace` под условием.
  Это тот самый «шаблон, живущий в обоих контекстах» (см. 4.1): после миграции — два
  независимых файла, `@theme/pages/result.twig` и `@admin/pages/result.twig`, и условие
  внутри шаблона исчезает вместе с ним.
* **Две темы — это одна тема, форкнутая копипастом.** Замеры:
  `templates/system` совпадает байт-в-байт в 8 файлах (alert, breadcrumbs, pagination,
  model_paginator, error/404, все шаблоны писем); из различающихся `sidebar-user-menu`
  отличается на 2 строки из 89, `debug` — на 8 из 47. В `src`: 9 js-файлов и 10 scss-партиалов
  идентичны, `_variables.scss` отличается на 3 строки из 240, `app.scss` — на 3 из 38.
  Реально форкнуты только `_base_styles.scss` (166 строк из 307), `main.js` (47/135),
  `error/403` (27/38) и сами layout'ы. Это главный аргумент за слияние тем: сейчас правка
  в `default` требует ручного повтора в `admin`, и «починили тут, забыли там» уже случалось.
* ~~Маршруты регистрируются условно, по правам текущего пользователя~~ — **снято**: отказ от
  условной регистрации уже в планах, доступы уезжают в middleware. Механизм для этого готов
  (`Route::middleware()`, `AdminAccessMiddleware`, `SuperAdminAccessMiddleware`), нужен только
  перевод оставшихся `if ($user->rights >= 9) { $router->map(...) }`.
  Для этого плана следствие только одно и отложенное: когда таблица маршрутов перестанет
  зависеть от пользователя, Twig-функция `path()` станет безопасной (имя маршрута существует
  всегда, а разрешён ли переход — решает middleware). Саму `path()` в эту миграцию не берём
  (решение от 04.08.2026), URL'ы в шаблонах остаются строками. Когда дойдёт до неё: `path()`
  даёт ссылку, но не право — пункт меню по-прежнему прячется проверкой прав.
* Vite-конфиг перечисляет темы вручную — нарушает дух требования №6 для ресурсов.

## 5. Разбор требований и варианты реализации

### 5.1. Требование 1 — фоллбэк шаблонов

**Варианты загрузчика:**

| Вариант | Суть | Сложность | Расширяемость | Производительность |
| --- | --- | --- | --- | --- |
| **B1. Один `FilesystemLoader`, несколько путей на namespace** | `addPath($dir, $ns)` в нужном порядке; Twig сам идёт по списку | минимальная (0 своего кода) | достаточная | лучшая: путь резолвится один раз и кэшируется в `$loader->cache` |
| B2. `ChainLoader` из трёх `FilesystemLoader` | по загрузчику на уровень | средняя | та же | хуже: `exists()` опрашивает N загрузчиков, ошибки менее внятные |
| B3. Свой `LoaderInterface` | полный контроль | высокая | нужна только для шаблонов из БД / из ZIP | своя реализация кэша ключей |

**Рекомендация: B1.** Требуемая цепочка выражается напрямую:

```php
// namespace модуля
$loader->addPath(THEMES_PATH . 'mytheme/templates/news', 'news');   // текущая тема
$loader->addPath(THEMES_PATH . 'default/templates/news', 'news');   // дефолтная тема
$loader->addPath(MODULES_PATH . 'news/templates',        'news');   // модуль

// namespace'ы темы: @theme (общее и публичное) и @admin (админская вёрстка)
$loader->addPath(THEMES_PATH . 'mytheme/templates',       'theme');
$loader->addPath(THEMES_PATH . 'default/templates',       'theme');
$loader->addPath(THEMES_PATH . 'mytheme/templates/admin', 'admin');
$loader->addPath(THEMES_PATH . 'default/templates/admin', 'admin');
```

`FilesystemLoader::getCacheKey()` возвращает **найденный путь**, поэтому переопределённый
темой шаблон и оригинал модуля — разные записи кэша; отравления кэша между темами быть не может.

**Уточнение к требованию:** делать цепочку не трёхуровневой, а произвольной длины — тема
объявляет `parent` в манифесте (`themes/mytheme/theme.php`), реестр раскрывает цепочку
`mytheme → base → default → module`. Стоимости это не добавляет, а дочерние темы («тот же
default, но другие цвета») становятся возможны сразу.

Регистрируем `is_dir()`-фильтром: `FilesystemLoader::addPath()` бросает исключение на
несуществующем каталоге. При ~22 модулях × 3 уровня это ~66 `is_dir` на сборку окружения;
на проде список путей кэшируется в PHP-файл рядом с кэшем контейнера.

**Контрольный пример — тема `example`** (см. 2.1): один файл `homepage/index`, layout и
ресурсы из дефолтной темы. После миграции она должна работать так же, переехав в
`themes/example/templates/homepage/index.twig` + `theme.php` с `parent: default`. Это
самый дешёвый функциональный тест всей цепочки фоллбэка — держим его зелёным начиная
с пилота (этап 2, там как раз мигрируется `homepage`).

### 5.2. Требование 2 — окружения и namespace'ы

> Раздел переписан 04.08.2026. Исходное требование («админка — отдельное окружение, темы
> админки и сайта не пересекаются») пересмотрено: см. журнал решений в 3.1.

**Правило, по которому проводится граница:**

> **Разные возможности → разные окружения. Разная вёрстка → разные namespace'ы.**

У админки и публички возможности одинаковые: тот же запрос, юзер, csrf, локаль, ассеты,
Vite. Отличается только вёрстка → это namespace'ы `@admin` и `@theme` внутри одного
окружения. У почты и инсталлятора отличаются именно возможности (нет запроса, csrf, Vite;
инсталлятор вообще работает до конфигурации) → это отдельные окружения.

**Варианты, которые рассматривались:**

| Вариант | Оценка |
| --- | --- |
| A1. Одно окружение, две темы, определение «админка или нет» по запросу (**как сейчас**) | ❌ имя `system::layout/default` означает два разных файла, по шаблону не понять какой; требует сниффинга `$_SERVER` в двух местах; ломается в CLI |
| A2. Отдельный `Environment` на админку | ❌ **та же неявность**: имя `@theme/layouts/default.twig` одинаково в обоих мирах, источник по файлу не читается. Плюс частичные отличия вёрстки приходится копировать целиком — админское окружение по определению не видит публичный шаблон, наследовать нечего |
| **A3. Одно окружение `web`, namespace'ы `@theme` и `@admin`** | ✅ **принято**: источник виден в самом шаблоне, частичные отличия решаются наследованием между namespace'ами, один кэш, общие компоненты компилируются один раз |
| A4. Одно окружение, подмена loader'а на запрос | ❌ технически невозможно: `Environment::addGlobal()` после инициализации рантайма бросает `LogicException`, а набор расширений входит в хэш опций компиляции |

**Как это выглядит в шаблоне** — источник виден при чтении файла, без знания о том, какой
URL его вызвал:

```twig
{% extends '@admin/layouts/default.twig' %}   {# админская страница #}
{% extends '@theme/layouts/default.twig' %}   {# публичная страница #}
```

**Шаблоны, живущие в обоих контекстах** (`error/403`, `error/404`, `pages/result`), — это
два независимых файла, `@theme/pages/…` и `@admin/pages/…`, даже когда вёрстка совпадает
(решение от 04.08.2026). Их единицы, а плата за «умную» экономию — вопрос «а этот файл
чей?» при каждом чтении.

Наследование между namespace'ами при этом **остаётся доступным** — Twig не запрещает
`{% extends '@theme/…' %}` из `@admin/…`, и это полезно, когда админский вариант отличается
подвалом:

```twig
{# @admin/pages/errors/403.twig — если автор темы решит не копировать #}
{% extends '@theme/pages/errors/403.twig' %}
{% block layout %}@admin/layouts/default.twig{% endblock %}
{% block actions %}<a href="/admin/">{{ __('To the admin panel') }}</a>{% endblock %}
```

Но базовый набор темы на этом не строится: по умолчанию файлы независимые. Обратное
направление (публичный шаблон наследует админский) запрещено линтом.

**Итоговые окружения:**

| Окружение | Что рендерит | Почему отдельное |
| --- | --- | --- |
| `web` | все HTTP-страницы: и `@theme/…`, и `@admin/…` | — |
| `mail` | письма из очереди | нет запроса, юзера и csrf; нужны абсолютные URL; `vite()` должен быть **недоступен физически**, а не по договорённости; локаль — параметр рендеринга, своя на каждое письмо (4.2) |
| `install` | инсталлятор | работает до конфигурации: нет БД, `config('modules')`, `skindef` — общее окружение там просто не собрать |

**Изоляция админского и публичного** перестаёт быть структурной гарантией и становится
структурой + дисциплиной, подстрахованной проверкой:

* админская вёрстка лежит в `@admin/…`, модульные админские страницы — в
  `modules/<m>/templates/admin/…`; нарушение видно при чтении файла;
* линт в `verify.sh`: шаблон под `templates/public/` не должен упоминать `@admin/`.
  Направление проверяется только одно — админскому шаблону наследовать публичный **можно и
  нужно** (пример выше);
* проверка греп-уровня намеренно простая: её задача — поймать опечатку и невнимательность,
  а не построить периметр безопасности. Периметр здесь дают права на маршрутах, а не
  видимость шаблонов.

**Что это дало сверх изоляции:** один кэш вместо трёх, общие компоненты (`pagination`,
`alert`, `breadcrumbs`) компилируются один раз, а не в каждом окружении, и исчезает вопрос
«в какое окружение регистрировать расширение модуля» — теги `.frontend`/`.admin` не нужны.

### 5.3. Требование 3 — ресурсы

`AssetResolver` получает **ту же цепочку тем**, что и загрузчик шаблонов, только оперирует
каталогом `assets` и отдаёт URL.

```
asset('images/logo.svg')      → /themes/<первая тема, где файл есть>/assets/images/logo.svg
asset('images/logo.svg', versioned: true) → ...?v=<mtime>
```

Изменения к текущему поведению:

* админка получает цепочку (сейчас — жёстко только `admin`); при цепочке из одного элемента
  поведение то же;
* **не бросать исключение** на отсутствующем файле в prod: возвращать `null`/пустую строку и
  писать в лог (в DEBUG — бросать). Тогда исчезает `try/catch` вокруг `flatpickr` в layout'е.
  Плюс функция `asset_exists()` для явных проверок;
* `vite()` остаётся, но точка входа берётся из манифеста темы (см. 6.2), а не из строки в
  layout'е — тогда layout дефолтной темы, унаследованный дочерней темой, подтянет **её**
  бандл, а не чужой.

### 5.4. Требование 4 — layout'ы

`{% extends %}` покрывает требование целиком: страница сама называет layout, layout'ы могут
наследоваться друг от друга, блоки переопределяются точечно.

Предлагаемый набор для темы (вместо сегодняшних четырёх layout'ов, размазанных по двум темам):

```
@theme/layouts/base.twig      — <html>, <head>, meta/styles/scripts, тело без хрома
@theme/layouts/default.twig   — extends base: сайдбар, шапка, футер, хлебные крошки
@theme/layouts/empty.twig     — extends base: только контент (AJAX-фрагменты, модалки)

@admin/layouts/default.twig   — extends @theme/layouts/base: админский хром и свой vite-вход
@admin/layouts/guest.twig     — extends @theme/layouts/base: центрированная карточка (вход в админку)
```

Админские layout'ы наследуют **общий** `base` — то есть `<head>`, мета, подключение локали и
цветовая схема живут в одном месте, а различаются только хром и точка входа сборки. Сегодня
это две независимые копии одного файла.

Блоки: `title`, `meta`, `styles`, `page_title`, `breadcrumbs`, `content`, `sidebar_user`,
`sidebar_menu`, `footer_content`, `scripts`.

Соответствие текущим конструкциям:

| Plates | Twig |
| --- | --- |
| `$this->layout('system::layout/default')` | `{% extends '@theme/layouts/default.twig' %}` |
| `$this->section('x', $default)` | `{% block x %}…default…{% endblock %}` в layout'е |
| `$this->start('x') … $this->stop()` | `{% block x %}…{% endblock %}` на странице |
| `$this->push('scripts')` | `{% block scripts %}{{ parent() }}…{% endblock %}` |
| `$this->sectionReplace('sidebar-menu', …)` | `{% block sidebar_menu %}…{% endblock %}` |
| `$this->fetch('ns::partial', [...])` | `{% include '@ns/partial.twig' with {...} only %}` |

**Динамический выбор layout'а.** Нужен для тех действий, что отдают фрагмент для модалки.
Два способа, оба поддерживаем:

1. статически — `{% extends '@theme/layouts/empty.twig' %}` в отдельном шаблоне фрагмента;
2. динамически — `{% extends layout|default('@theme/layouts/default.twig') %}`, а контроллер
   кладёт `layout` в данные (или `ViewResponse::withLayout()`). Не злоупотреблять: Twig не
   может закэшировать разрешение родителя, если он вычисляемый.

### 5.5. Требования 5 и 6 — namespace'ы и отсутствие конфигурации

**Варианты регистрации:**

| Вариант | Оценка |
| --- | --- |
| C1. Лениво, из контроллера (как сейчас) | ❌ сохраняет сегодняшний баг «шаблон B не виден, если контроллер B не создавался»; в Twig ещё хуже: `Environment` кэширует загруженные шаблоны в памяти, добавление пути после первой загрузки даёт неконсистентную резолюцию внутри запроса |
| **C2. Все namespace'ы при сборке окружения, по соглашению** | ✅ имя модуля из `config('modules')` → `@<module>`; пути — по соглашению; новый модуль в списке установленных подхватывается сам |
| C3. C2 + тег `johncms.template_paths` для нестандартных случаев | ✅ добавка к C2 для тех, кому мало одного namespace |

**Рекомендация: C2 + C3.** Требование 6 выполняется буквально: конфигурация Twig не трогается
вообще, модуль объявляется в `config/autoload/modules.global.php` (как сейчас) и кладёт файлы
по соглашению.

Раскладка каталогов модуля. Контекст виден в самом имени шаблона — это та же явность, что и
у `@theme` / `@admin`:

```
modules/news/templates/public/index.twig  → @news/public/index.twig
modules/news/templates/admin/index.twig   → @news/admin/index.twig
modules/news/templates/mail/digest.twig   → @news/mail/digest.twig   (окружение mail)
```

Соответственно и переопределение в теме зеркалит структуру:
`themes/mytheme/templates/news/admin/index.twig`.

Сейчас так разложен только модуль `news`; у остальных шаблоны лежат плоско, разложить их по
`public/` и `admin/` придётся при миграции каждого модуля — это уже учтено в этапах 3 и 4.

`libraryHelpers` из модуля library в отдельном namespace не нуждается — становится
`@library/public/helpers/…`.

### 5.6. Требование 7 — автоэкранирование

`autoescape: 'html'`, `strict_variables: DEBUG`.

По `strict_variables`: в prod `false` (страница не должна падать из-за необъявленной
переменной), в dev `true` — тогда проблема ловится у разработчика, а не у посетителя.
CI гоняет тесты с `DEBUG=true`. В шаблонах идиомы `x|default('')`, `x is defined`,
`x ?? ''` вместо сегодняшних `isset()/empty()`.

**Аудит перед включением (обязательно, иначе получим или дыры, или битую вёрстку).**
Сегодня «неэкранированный вывод» бывает трёх видов, и различить их может только человек:

1. `<?= $this->e($x) ?>` → `{{ x }}`. Механически, безопасно. ~737 мест.
2. `<?= $x ?>`, где данные заведомо HTML (BBCode после парсера, `HTMLPurifier::purify()`,
   реклама, счётчики, смайлы, пагинация, тексты уведомлений) → должно остаться HTML.
3. `<?= $x ?>`, где экранирование **забыли** — это баг, и Twig его чинит сам.

Пункты 2 и 3 различаются только чтением кода, поэтому каждый шаблон при миграции проходит
явную проверку — это часть чек-листа этапа, а не «потом посмотрим».

**Решение для пункта 2 лучше, чем `|raw` в шаблоне.** Сервисы, которые по контракту
возвращают готовый HTML, должны возвращать `Twig\Markup` — Twig не экранирует его повторно:

```php
public function render(): Markup            // Pagination::render()
public function purify(string $html): Markup // обёртка над HTMLPurifier
public function parse(string $bbcode): Markup
```

Тогда `{{ pagination.render() }}` и `{{ article.text|bbcode }}` работают без `|raw`, а `|raw`
в шаблоне становится **сигналом ревьюеру** («здесь автор решил сам»), а не рутиной. Кандидаты:
`Http\Pagination\Pagination`, `Ads`, `Counters`, `Smilies\SmiliesRenderer`, `HTMLPurifier`-обёртка,
`Notifications` (шаблоны событий из `config/notifications.global.php`).

**Отдельная ловушка:** часть переводимых строк содержит разметку — `config/places.global.php`
и `config/notifications.global.php` целиком состоят из строк вида
`'<a href="#home#/forum/">…</a>'`, и в шаблонах есть `sprintf(d__('system', '…%s…'), '<a …>')`.
После включения autoescape они выведутся как текст с тегами. Их надо либо провести через
`Markup`, либо явно пометить `|raw` — и это надо перечислить списком до миграции, потому что
визуально такая регрессия незаметна на большинстве страниц.

**Контексты, которые autoescape не покрывает:** внутри `<script>` Twig не переключается на
JS-стратегию сам. Правила в гайд: `{{ x|e('js') }}` в JS-литералах, `{{ data|json_encode|raw }}`
для передачи структур, `{{ x|e('html_attr') }}` в незакавыченных атрибутах, `|e('url')`
для сегментов URL.

### 5.7. Требование 8 — компоненты

| Вариант | Когда применять | Стоимость |
| --- | --- | --- |
| **Макросы** (`{% macro icon(name) %}`) | атомы: иконка, бейдж, кнопка, аватар | 0, часть Twig |
| **`include … with … only`** | партиалы с данными (карточка темы форума, строка пользователя) | 0 |
| **`embed`** | контейнеры со слотами (модалка, карточка, таблица с заголовком) | 0 |
| `twig/html-extra` | `html_classes()`, `html_attr()` | +1 маленький пакет, опционально |
| Symfony UX TwigComponent | компоненты-классы с логикой | ❌ не сейчас: без FrameworkBundle требует ручной проводки фабрики, рендерера и стека; выигрыш не окупает |

**Рекомендация:** соглашение вместо фреймворка.

```
themes/<name>/templates/components/   — компоненты темы
modules/<m>/templates/*/components/   — компоненты модуля
themes/<name>/templates/macros/ui.twig — атомы
```

Правила: у компонента шапка с описанием пропсов (`{# @param string title #}`), подключение
**всегда** с `only` (компонент не читает окружающий контекст — иначе он не переиспользуем и
ломается при переносе), никаких обращений к глобальным сервисам внутри.

Сегодняшние `system::app/*` (alert, breadcrumbs, pagination, sidebar-*) переезжают в
`@theme/components/*` — это готовый первый набор.

### 5.8. Требование 9 — функции, фильтры, глобалки

**Глобалки — одна.** `app` — тонкий объект над `RequestStack` (по образцу Symfony `AppVariable`,
и по правилу из `.agents/architecture.md` «шаблон получает факты, а не запрос»):

```
app.user            app.locale        app.color_scheme (dark/light/auto)
app.csrf_token      app.is_home_page  app.environment   app.theme (имя темы)
app.cms_version     app.debug
```

Всё ленивое: обращение к `app.user` резолвит сервис, необращение — нет.

**Функции:**

| Функция | Замена чему |
| --- | --- |
| `__('…')`, `d__('domain', '…')`, `dn__()` | те же helpers |
| `asset(path, versioned = false)`, `asset_exists(path)` | `$this->asset()` |
| `vite(entry = null, rtl = null)` | `$this->vite()` |
| `avatar(user_id)` | `$this->avatar()` |
| `config('johncms.copyright')` | глобал `$config` (массив целиком больше не отдаём) |
| ~~`path()` / `url()`~~ | **не в этой миграции** (решение от 04.08.2026): URL'ы в шаблонах остаются строками, функции появятся отдельной задачей, возможно вместе с редизайном |

**Фильтры:** `format_number`, `format_size`, `display_date`, `purify`, `bbcode`, `smilies`
(последние три возвращают `Markup`).

**Не экспортируем принципиально** (это половина ценности перехода):
`di()`, `container`, `$config` целиком, доступ к произвольным константам/классам,
`{{ constant() }}`, `{{ attribute() }}` на сервисах. Если шаблону что-то нужно — это либо
факт в `app`, либо аргумент, либо новая явная функция.

### 5.9. Требование 13 — сосуществование движков

**Варианты:**

| Вариант | Гранулярность | Стоимость | Проблемы |
| --- | --- | --- | --- |
| I1. Флаг в манифесте модуля | модуль | реестр + конфиг + ветвление | модуль мигрирует целиком (forum — 32 шаблона за раз); ветка «модуль на Twig, но шаблон ещё нет» невыразима |
| **I2. По форме имени шаблона** | **шаблон** | ~40 строк | требует, чтобы имена не пересекались — они и не пересекаются |

**Рекомендация: I2.** Имена уже синтаксически различимы:

```
'@news/index.twig'  → Twig      (начинается с @)
'news::index'       → Plates    (содержит ::)
```

`DelegatingRenderer implements RendererInterface` смотрит на первый символ и делегирует.
Ни реестра, ни конфигурации, ни «перевода модуля целиком»; мигрировать можно по одной
странице, admin- и public-части модуля — независимо.

**Мост между движками.** Партиалы без layout'а и секций (`pagination`, `breadcrumbs`, `alert`,
`model_paginator`, `user_row`) вызываются из обоих движков:

* из Twig: `{{ plates('system::app/pagination', {items: items}) }}` — временная функция,
  возвращает `Markup`;
* из Plates: `$this->fetch()` продолжает работать со своими шаблонами как раньше.

**Чего мост не умеет:** Plates-страница не может отнаследоваться от Twig-layout'а (секции
Plates внутренние и наружу не отдаются). Значит на время миграции **layout'ы существуют в
двух копиях** (`layouts/default.twig` + `layout/default.phtml`). Копий мало — 4 (публичный,
админский, guest, почтовый), но они расходятся, если окно миграции длинное. Отсюда порядок
этапов в разделе 8: публичная часть мигрируется целиком и подряд (этап 3), потом админская
(этап 4), и `.phtml`-layout удаляется сразу по завершении своей части, а не в конце.

### 5.10. Требование 14 — API рендеринга

Два уровня, оба нужны:

```php
interface RendererInterface
{
    public function render(string $template, array $data = []): string;
    public function exists(string $template): bool;
}
```

Реализации: `TwigRenderer`, `PlatesRenderer` (адаптер над текущим `Render`),
`DelegatingRenderer` (диспетчер, он же регистрируется как `RendererInterface`).

Второй уровень — **предпочтительный для новых контроллеров**: контроллер не рендерит, а
возвращает описание представления:

```php
return new ViewResponse('@news/index.twig', ['articles' => $articles]);
```

`ResponseNormalizer` уже принимает `Response|string|null` — добавляется четвёртая ветка.
Что это даёт:

* контроллер не знает ни о движке, ни об окружении (окружение выбирает ядро по запросу);
* unit-тест контроллера проверяет имя шаблона и данные, ничего не рендерит;
* ложится в уже идущую миграцию HTTP-ядра (`.claude/http-kernel-migration-plan.md`).

Размещение: `system/src/Http/View/ViewResponse.php` (это HTTP-слой, рядом с
`ResponseNormalizer`). Имя утверждено 04.08.2026. Суффикса `*Response` в списке `AGENTS.md`
нет — при уборке (этап 6) добавить его туда, чтобы правило и код не расходились.

### 5.11. Требование 10 — кэш

```php
'cache'       => CACHE_PATH . 'twig/' . $environment,   // data/cache/twig/{web,mail,install}
'auto_reload' => DEBUG,
'debug'       => DEBUG,
```

* `data/` вне `public/` — скомпилированные шаблоны недоступны по URL. ✅
* `cache:clear` уже чистит `data/cache` целиком — работает без изменений; в описание команды
  добавить упоминание Twig.
* Новая команда `twig:compile` — прогрев кэша при деплое (иначе первый посетитель компилирует
  290 шаблонов). Регистрируется как обычная консольная команда (тег `johncms.console_command`).
* Новая команда `twig:lint` — синтаксическая проверка всех шаблонов; **добавить в
  `.agents/scripts/verify.sh`**, иначе синтаксическая ошибка в шаблоне не ловится ни phpcs,
  ни phpstan, ни тестами.
* В prod держать `auto_reload = false` (иначе `stat()` на каждый шаблон каждого запроса) и
  включённый opcache.

### 5.12. Требование 11 — расширяемость

Паттерн в проекте уже есть (`johncms.sitemap_provider`, `johncms.console_command`,
`tagged_iterator`). Повторяем:

```php
// modules/forum/config/services.php
$services->set(ForumTwigExtension::class)->tag('johncms.twig_extension.frontend');
$services->set(ForumTemplatePaths::class)->tag('johncms.template_paths');
```

Теги: `johncms.twig_extension` (окружение `web`, то есть весь HTTP — и публичная часть, и
админка) и `johncms.twig_extension.mail` (узкий набор для писем). Отдельного тега для админки
не нужно — после решения от 04.08.2026 админка и публичка живут в одном окружении, и это
одно из упрощений, которое оно дало.

Зависимости расширений — через `ContainerRuntimeLoader`, чтобы регистрация функции не тянула
за собой инстанцирование сервиса.

**Чего не даём модулям:** мутировать глобалки на лету (`addGlobal` после старта рантайма —
исключение Twig, и это правильно) и добавлять пути к чужим namespace'ам.

### 5.13. Требование не из списка — извлечение переводов из `.twig`

Без этого при первой же миграции шаблона его строки выпадут из `.pot` и переводы потеряются
на всех 20+ языках. **Блокирующее требование для этапа 1.**

| Вариант | Оценка |
| --- | --- |
| O1. Компилировать Twig в PHP и сканировать компилят существующим `PhpScanner` | ❌ ненадёжно: Twig компилирует вызов функции в обращение к extension/callable, имя `__` в коде не сохраняется |
| **O2. Свой экстрактор по AST Twig** | ✅ `$twig->parse($twig->tokenize(new Source(...)))`, обход дерева, сбор `FunctionExpression` с именами `__`/`d__`/`dn__` и константным первым аргументом; ~80 строк, точные номера строк, нет ложных срабатываний |
| O3. `symfony/translation` extractor | ❌ тянет другой пакет и другой формат сообщений |

**Рекомендация O2**, вторым проходом в `I18nScanCommand`, результат сливается в тот же `.pot`.
`translate.xml.dist` менять почти не нужно — он оперирует каталогами; надо расширить фильтр
расширений и добавить каталоги тем.

**Отклонённый вариант** (решение от 04.08.2026): `NodeVisitor`, переписывающий на компиляции
`__('Текст')` в `d__('<namespace шаблона>', 'Текст')`. Технически работает и убирает
рантайм-состояние «текущий домен», но вводит неявное правило, которого нет больше нигде в
системе: одна и та же запись `__()` означала бы разное в PHP и в шаблоне. Остаётся текущее
поведение — домен по умолчанию ставит контроллер (`initModule()`), шаблон пользуется им.

Следствие, которое надо знать: шаблон одного модуля, подключённый из другого, возьмёт домен
вызывающего. Это осознанно оставлено как есть — случай редкий, а лечится явным `d__()`.
Экстрактор при этом всё равно считает домен по пути файла, как и `translate.xml`, поэтому
строка попадёт в `.pot` своего модуля; расхождение возможно только если такое подключение
кто-то сделает.

## 6. Структура темы (требование 12)

### 6.1. Дерево

Тема одна на весь сайт — админская вёрстка живёт в ней же, в подкаталоге `admin/`
(решение от 04.08.2026, см. 3.1 и 5.2).

```
themes/<name>/
├── theme.php                  манифест (см. 6.2)
├── templates/
│   ├── layouts/               base.twig, default.twig, empty.twig
│   ├── components/            alert.twig, breadcrumbs.twig, pagination.twig, sidebar-*.twig
│   ├── macros/                ui.twig
│   ├── pages/                 errors/403.twig, errors/404.twig, result.twig
│   ├── admin/                 ← namespace @admin
│   │   ├── layouts/           default.twig, guest.twig
│   │   ├── components/        sidebar-admin-menu.twig, …
│   │   └── pages/             errors/{403,404}.twig, result.twig  (отдельные файлы)
│   ├── mail/                  layouts/ + templates/        ← окружение mail
│   └── <module>/              переопределения шаблонов модулей:
│       └── news/{public,admin}/…
├── assets/                    статика темы (см. 6.3)
├── src/
│   ├── js/                    public.js, admin.js — две точки входа
│   └── scss/{shared,public,admin}/
└── locale/                    опционально: строки самой темы, домен theme.<name>
```

Namespace'ы:

* `@theme` → `templates/` текущей темы → родительской → дефолтной;
* `@admin` → `templates/admin/` по той же цепочке;
* `@<module>` → `templates/<module>/` темы → … → `modules/<module>/templates/`.

Тема, которой админка не интересна, просто не заводит каталог `admin/` — namespace `@admin`
целиком отработает по фоллбэку из дефолтной темы. Тема, которой интересна, переопределяет
ровно те файлы, которые хочет. Если переопределение получилось кривым — файл удаляется,
и всё возвращается к дефолтному; никакого opt-in-флага в манифесте для этого не нужно.

**Разделение JS/CSS.** Публичная страница не должна тянуть админский бандл. Механизм для
этого уже работает и слиянием тем не ломается: сборка одна, входов два, в текущем
`public/build/manifest.json` видно общий `_vendor-*.js` и раздельные CSS у каждого входа.
После слияния — те же два входа внутри одной темы (`src/js/public.js`, `src/js/admin.js`),
`@theme/layouts/base.twig` объявляет блок `{% block vite %}`, а `@theme/layouts/default.twig`
и `@admin/layouts/default.twig` подставляют туда свою точку входа.

Реальная работа тут не в сборке, а в SCSS: `_base_styles.scss` в двух темах форкнут на
166 строк из 307, его надо руками разложить на `shared/` + `public/` + `admin/`, иначе правка
публичных стилей начнёт менять админку. Остальные партиалы почти идентичны (`_variables.scss`
— 3 строки различий из 240), они сливаются механически.

### 6.2. Манифест `theme.php`

```php
return [
    'name'    => 'Dark Blue',
    'parent'  => 'default',              // цепочка фоллбэка; null = сама себе корень
    'entries' => [                       // точки входа Vite
        'public' => 'themes/dark-blue/src/js/public.js',
        'admin'  => null,                // null = взять из родительской темы
    ],
    'settings' => [                      // опционально, доступно как app.theme.settings.*
        'accent_color' => '#586776',
    ],
];
```

Что это чинит:

* `parent` — N-уровневый фоллбэк без кода;
* `entries` — `vite.config.js` перестаёт перечислять темы руками: маленький скрипт собирает
  входы из всех манифестов (требование 6 применительно к сборке). `null` у входа означает
  «своей сборки нет, взять бандл родителя» — тема, меняющая только шаблоны (как `example`),
  вообще не собирается;
* `settings` — заявленные в требовании 12 «собственные настройки темы»; на первом этапе просто
  значения по умолчанию из манифеста, админ-UI — отдельной задачей.

### 6.3. Развилка по ресурсам (нужно решение)

Сейчас тема физически разорвана на два дерева: `themes/<name>/{src,templates}` и
`public/themes/<name>/assets`. Скачиваемая тема — это два архива в разные места.

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| R1. Оставить как есть | 0 работы | тема не переносима одним каталогом; фоллбэк ресурсов считается по одному дереву, а отдаётся из другого |
| **R2. `themes/<name>/assets` — источник истины + команда `theme:publish`** (симлинк в `public/themes/<name>/assets`, копирование как fallback для хостингов без симлинков) | тема = один каталог; ставится/удаляется целиком | +1 шаг при установке темы и при деплое |

**Принято R1** (04.08.2026): оставляем как есть. Команда публикации — лишний шаг, который
пользователю пришлось бы объяснять, а основную задачу текущая раскладка не блокирует.
К R2 можно вернуться позже, отдельной задачей.

Что при этом всё равно придётся сделать на этапе 4: свести `public/themes/admin/assets` и
`public/themes/default/assets` в один каталог — тема становится одна, значит и дерево
ресурсов у неё одно. Это часть слияния тем, а не смена схемы хранения.

Что всплыло по ходу и учтено:

* **`app.*` в шаблоне — snake_case.** Twig ищет атрибут по точному имени, `getColorScheme()`
  по `app.color_scheme` не находится. В `AppVariable` добавлены `__isset`/`__get`, которые
  разворачивают `snake_case` в геттер; имена из 5.8 работают как записаны.
* **Атрибут Eloquent-модели, которого нет, вызывает `__call`.** `app.user.rights` у гостя
  уходит в `User::rights()` и падает — `|default` не спасает, Twig при наличии `__call`
  считает метод существующим. В шаблонах всё, чего у гостя нет, закрыто
  `app.user.isValid and …`. Для этапа 3 это правило в чек-лист; если станет мешать —
  отдельной задачей дать гостю дефолтные атрибуты или заводить для шаблонов узкий объект.
* **`vite()` принимает область** (`public`/`admin`), а не путь: точка входа берётся из
  манифеста темы через `ThemeEntryResolver` (5.3), поэтому унаследованный layout тянет бандл
  дочерней темы.
* **Строковые литералы escaper считает безопасными** — HTML внутри `{{ '<b>' }}` выводится
  разметкой. В шаблоне-документации `themes/example` пришлось ставить явный `|e`.
* Алиас `Counters::class → 'counters'` переехал из `modules/notifications` в ядро

  от установки. Четыре записи из baseline, державшиеся на этом, удалены.

## 11. Инвентаризация вывода (результат этапа 0)

Вход для этапа 3: что после включения autoescape должно остаться разметкой, а не превратиться
в текст с тегами. Замеры от 04.08.2026.

### 11.1. Сервисы и методы, возвращающие готовый HTML

Кандидаты на возврат `Twig\Markup` (5.6) — тогда шаблон пишет `{{ x }}` без `|raw`:

| Источник | Что отдаёт | Где виден в шаблонах |
| --- | --- | --- |
| `Http\Pagination\Pagination::render()` | готовый блок пагинации (рендерит `system::app/pagination`) | `$pagination` / `$data['pagination']`, ~109 мест |
| `Ads::getAds()` | массив рекламных блоков, значения — произвольный HTML администратора | `$ads_array`, 10 мест (оба layout'а) |
| `Counters::counters()` | коды счётчиков посещаемости (внешние `<script>`) | `$analytics` в обоих layout'ах |
| `Counters::users()` | `12&#160;/&#160;<span class="red">+3</span>`; помечен `@deprecated` в пользу `usersCounters()` | сайдбары |
| `Smilies\SmiliesRendererInterface::render()` | текст с `<img>` смайлов | через презентеры модулей: album, downloads, forum, комментарии |
| `\HTMLPurifier::purify()` | очищенный пользовательский HTML | 30 вызовов; тексты форума, комментариев, новостей, гостевой, библиотеки, коллекций, профиля, личных сообщений, согласий |
| `Utils\PlainTextFormatter::toHtml()` | `nl2br(htmlspecialchars($text))` — экранирование **уже внутри** | презентеры album и др. |
| `Users\UserPlaceFormatterInterface::format()` | ссылка «где сейчас пользователь», собранная из `config/places.global.php` | списки онлайна, профиль |
| `config/notifications.global.php` → `events.*.message` | замыкания, собирающие HTML уведомления | модуль notifications |
| `Comments` | сам печатает через `echo $this->view->render(...)` — не сервис, а генератор страницы; разбирать отдельно при миграции комментариев | — |

Отдельно: `config/autoload/bbcode.global.php` **никем не используется** (в коде нет ни одного
обращения к `config('bbcode')`). BBCode-парсера в 9.9 нет, тексты чистит HTMLPurifier. Значит
фильтр `bbcode` из 5.6 не нужен, а сам конфиг — кандидат на удаление отдельной задачей.

### 11.2. Переводимые строки с разметкой

**44 вызова `__()`/`d__()` с тегами внутри msgid** — после autoescape выведутся как текст.
Распределение: `modules/admin` 10, `modules/forum` 6, `modules/downloads` 4,
`modules/profile` 3, `modules/registration` 3, `modules/homepage` 2, по одному в
album, guestbook, library (3), mail, news, а также 8 в шаблонах писем обеих тем.
Почти все — `<br>` внутри подсказок и предупреждений; содержательная разметка в
`<h3>WARNING!</h3>` (2 шаблона удаления разделов форума в админке) и
`'You are not logged in. You must be <a href="/login/">logged in</a> to comment.'`
(`modules/news/templates/public/article.phtml`).

Найти заново: `grep -rn "d\?n\?__(\s*'[^']*<[a-z/]" --include='*.php' --include='*.phtml' system/ modules/ config/ themes/`

**Целиком состоят из строк с разметкой два конфига:**

* `config/places.global.php` — 20 строк вида `'<a href="#home#/forum/">' . d__('system', 'Forum') . '</a>'`;
  переводится только текст ссылки, теги — вокруг него. Уходит через `UserPlaceFormatter`, то
  есть лечится одним `Markup` в форматтере, а не правкой строк.
* `config/notifications.global.php` — тексты событий с `<b>`, `<a href="#…#">`, `<div class="…">`;
  часть собирается замыканиями. Здесь разметка внутри самого msgid, и её придётся либо
  проводить через `Markup`, либо оставлять `|raw` на выводе уведомления.

### 11.3. Массовые формы вывода в `.phtml`

Всего в шаблонах 3862 конструкции `<?= … ?>` без `$this->e()`. Разбирать их поштучно на этапе 0
смысла нет — они уходят вместе с шаблонами; но состав важен для оценки этапа 3, и он на
90% безобиден:

| Что | Кол-во | После миграции |
| --- | --- | --- |
| вывод с `__()`/`d__()` внутри | 1936 | `{{ __('…') }}`, кроме 44 строк из 11.2 |
| `$this->asset(…)` (199 из них — `icons/sprite.svg`) | 233 | `{{ asset(…) }}`, экранирование безвредно |
| `$this->fetch(…)` внутри `<?= ?>` | 53 | `{% include %}` |

| `$csrf_token`, `$locale`, счётчики, id, урлы из конфига | остальное | безопасны, autoescape ничего не меняет |

остальное переводится механически.
