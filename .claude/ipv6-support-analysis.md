# Поддержка IPv6 — собранная фактура

Дата сбора: 2026-07-28. Ветка: `10.x`. **Это не план работ, а разведка**: снимок того, что придётся
тронуть, и решения, которые уже приняты, чтобы будущая миграция стоила дешевле.

Задача заведена отдельно от `.claude/http-kernel-migration-plan.md` сознательно: она требует
миграции схемы и данных, а HTTP-миграция требует, чтобы каждый коммит оставлял CMS деплоябельной.
Две рискованные вещи в одной ветке — способ не понять, что именно сломалось.

## Сегодняшнее состояние

Адреса хранятся как `bigint` (`ip2long`), то есть **только IPv4**. Посетитель с IPv6 записывается
как `127.0.0.1`: `Environment::toIpv4()` подменяет всё, что не проходит
`FILTER_VALIDATE_IP + FILTER_FLAG_IPV4`. Без подмены было бы хуже — `ip2long()` вернул бы `false`,
и в колонку уехал бы 0.

### Колонки (12 в 6 таблицах, все `bigint(20)`)

| Таблица | Колонки |
|---|---|
| `users` | `ip`, `ip_via_proxy` |
| `cms_users_iphistory` | `ip`, `ip_via_proxy` |
| `cms_sessions` | `ip`, `ip_via_proxy` |
| `forum_messages` | `ip`, `ip_via_proxy` |
| `guest` | `ip` |
| `cms_ban_ip` | `ip1`, `ip2` — **диапазон**, см. ниже |

Два модуля уже хранят адрес строкой — `varchar(45)`: `consent_log.ip_address`,
`contact_messages.ip_address`. То есть расхождение в проекте уже существует, и новый код
де-факто выбрал строку.

### Код

* Каст `Johncms\Casts\Ip` — `ip2long`/`long2ip` для Eloquent-моделей, единственная точка,
  через которую проходит большинство записей.
* `Johncms\Users\GuestSessionMutators` — свои мутаторы для `guest`, дублируют каст.
* Сырой SQL, каст не применяется: `system/src/Security/BanIP.php`,
  `system/src/System/Users/UserStat.php`, `system/src/System/Users/UserFactory.php`,
  `system/src/Comments.php`, `system/src/UserProperties.php`.
* Отображение (`long2ip` при выводе): `admin/HiddenTopicRowMapper`, `admin/HiddenPostRowMapper`,
  `admin/Ip/IpBanController`, `forum/ViewPollVotersUseCase`,
  `downloads/CommentsReviewController`, `profile/GetIpHistoryUseCase`.
* Поиск по IP: `admin/IpRangeParser` + `IpRangeParseResult` — разбирает `a.b.c.*`, `a.b.c.d - e.f.g.h`
  и маску в пару `ip2long`.
* Журнал частоты запросов: `system/src/Security/FileRequestRateLog.php` — формат записи
  `pack('LL', ip, time)`, 8 байт, тоже только IPv4.

## Два факта, определяющих решение

**1. Баны по диапазону.** `BanIP.php:34` — `whereRaw('? BETWEEN `ip1` AND `ip2`')`, и `IpRangeParser`
строит такие же диапазоны для поиска по IP в админке. На `varchar` это ломается: строковое
сравнение `'10.0.0.9' BETWEEN '10.0.0.10' AND '10.0.0.20'` даёт бессмыслицу. Поэтому «просто
хранить строками» — не решение для всей схемы.

Рекомендация: `varbinary(16)` + `INET6_ATON()` / `INET6_NTOA()` (есть в MariaDB и MySQL 5.6+).
Тогда `BETWEEN` работает, сортировка корректная, длина фиксированная, IPv4 живёт в
v4-mapped форме. Читаемость глазами в БД теряется — но её и сейчас нет, там `bigint`.
Отдельно продумать: диапазон должен задаваться в пределах одного семейства адресов, иначе
`BETWEEN` захватит чужое пространство.

Альтернатива — `varchar(45)` — годится только если баны по диапазону переписать на префиксы (CIDR)
с отдельной колонкой длины префикса и сравнением по префиксу, а не по диапазону.

**2. Механизма миграций схемы в проекте нет.** `public/install/lib/Database.php` — один
`createTables()` через Blueprint, начинающийся с `dropAllTables()`. Путь обновления схемы для
существующих установок отсутствует как класс. Значит IPv6 тянет за собой появление миграций —
и это самостоятельная задача, нужная проекту независимо от IPv6.

## Что уже сделано в подготовку (этап 5 HTTP-миграции)

* **Журнал частоты запросов изолирован** за `Johncms\Security\RequestRateLogInterface`: интерфейс
  оперирует адресами в текстовой форме, `pack('LL', …)` остался деталью файловой реализации.
  При переходе на IPv6 меняется только она.
* **Решено: long-форма не выходит за границу записи в БД.** В Application-слой и контроллеры
  адрес передаётся строкой; `ip2long` живёт в касте и в шести легаси-местах с сырым SQL.
  Благодаря этому IPv6-миграция сведётся к «сменить тип колонок + переписать каст + бэкфилл»
  без правок в модулях.

## Ориентировочный порядок работ (когда дойдут руки)

1. Механизм миграций схемы (нужен сам по себе).
2. Смена типа колонок на `varbinary(16)` + бэкфилл существующих данных (`INET6_ATON(INET_NTOA(ip))`).
3. Каст `Ip` и мутаторы `guest` — на `inet_pton`/`inet_ntop`; удалить дублирование.
4. Шесть мест с сырым SQL — либо на модели, либо на `INET6_ATON()` в запросе.
5. `IpRangeParser` / баны — диапазоны в бинарной форме, проверка семейства адресов.
6. Формат записи `FileRequestRateLog` (16 байт адреса + время).
7. Валидация ввода: сейчас `FILTER_FLAG_IPV4` стоит и в касте, и в `Environment` — снять.
8. Отображение: `long2ip` в шести местах вывода → форма из БД как есть.
